# AI 房间：需求澄清与确认流程

创建和修改统一使用「澄清需求 → 方案待确认 → 实施 → 完成」流程。

## 用户怎么用

1. 简单描述要解决的问题，可以附参考图片。
2. AI 每轮询问 2–4 个关键问题，显示逐题选项、推荐答案和生活化示例。推荐项不会自动替你勾选；不确定时可以选「你来推荐」，也能填写自己的答案。漏答时会定位提示，答案草稿保存在本机。如果首轮遗漏使用者／协作方式，工作台会额外补上一题。
3. 查看方案卡片的八项内容：使用场景、第一版功能、怎么使用、数据规模与保存、权限及用途、实施计划、验收标准、假设和限制。
4. 有意见直接发送，AI 修改后重新提交方案。满意后点击「同意方案，开始实施」。输入框里有未发送文字或图片时，先处理这些补充要求。
5. 实施完成后打开房间，按方案的验收标准检查。后续修改重新确认。

## Harness 约束

- `ask_room_questions` 接受可选短标题 `title`，以及结构化 `questions`：每题包含 `topic`（audience/data/features/other）、`title`、2–5 个 `options`、选项中的 `recommended` 和生活化 `example`。系统补充「你来推荐」选项。
- 必须区分个人使用、多人独立使用和共同编辑同一份数据，不能把离线房间各自的数据库描述成自动同步。

- `ask_room_questions` 保存问题并等待新的用户消息，模型不能在同一轮自问自答后进入方案阶段。
- `propose_room_plan` 保存结构化方案，并生成新的方案 ID。模型不具备批准方案的工具。
- 沟通阶段仅提供需求、方案和能力检查工具，不加载完整代码格式参考，减少不必要的输入 Token。
- 构建工具另有服务端检查，必须处于 implementing 且批准 ID 与当前方案一致。适用于声明式、3D 模板、自由房间的草拟、测试和安装。
- 确认由工作台界面通过现有受信 IPC 发送 `approvePlanId`。文字「好的」或「直接开始」不会被当作授权。
- 补充要求使旧方案确认失效，并清除旧自由房间草稿，避免误安装旧版本。
- 执行期间请等回复完成，或停止后再提交补充要求，避免旧方案和新需求交错执行。
- 方案持久保存；工作台重启中断实施后回到待确认阶段。模型初始化失败也恢复为可重试状态。
- 确认实施不代表授予房间的联网、AI、文件等运行权限，原权限系统仍生效。

## 验证与边界

聊天顶部常驻新对话入口，并区分「已有房间」与「修改需求沟通」等状态。每轮展示耗时，展开可查看历史轮次、模型、接口返回的输入／输出／缓存 Token。多次模型回复会累计；缺失字段标记未知或部分统计。Pi 模型目录费用仅作估算，零值或未提供价格不当作免费，不能用于推算订阅套餐实际账单；旧会话不追溯估算。

设置中提供标准／大／特大字号，正文对应 14／16／18px，辅助文字对应 12／14／16px。保存后同步工作台和 AI 独立窗口，不改变房间自身网页的排版。

离线假模型集成测试验证完整三轮流程、绕过阻断、旧方案失效、修改二次确认、重启恢复、声明式与自由房间生成及图片输入。Electron 冒烟测试检查问题和方案卡片、运行中禁用按钮，以及将模型文本作为纯文本显示。

本轮没有使用真实 API 评估各模型的追问质量。问题是否切中实际业务、默认值是否合适、实现是否完整符合方案，仍需要真实模型和场景验收；程序门禁保证不能在用户确认前构建，不保证模型每项业务判断都正确。
