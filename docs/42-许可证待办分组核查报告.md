# 许可证待办：分组核查报告

日期：2026-09-09。源码基线：`df34403`；检查对象包括当前源码与本机已有的 alpha.26 解包发行目录。它们不是同一状态：alpha.26 二进制早于后续许可证修订。

## 执行方式与结论

按用户要求，使用 3 个 `gpt-5.6-luna` 子智能体分组只读核查：AWS 3 项、历史小包 6 项、fontkit/Canvas。主智能体复核关键结论，并检查 Git/MinGit。不调用用户配置的 MiMo/Kimi API，不安装依赖，不下载大型源码，不联系上游或公开发帖。本轮没有实际费用明细，因此不声称具体节省金额。

**本轮没有充分证据关闭清单里的 10 项。** 这不等于已经认定这些包侵权或不能使用；它表示尚未按本项目要求确认足够的许可原文及版本关联。许可证元数据、完整许可文本、实际分发范围、对应源码提供是不同检查项，不应混在一起。

核查过程中拒绝了一条看似可用的线索：某索引指向 chainsaw 的版本 LICENSE，但直接访问并没有取得原文。因此没有据此抄入版权行或把该项标为完成。

## Git/MinGit：有明确进展，但源码义务尚未完成

1. 本地 MinGit 版本 `2.55.0.windows.3`；本地记录的 ZIP SHA-256 与 [官方发行页](https://github.com/git-for-windows/git/releases/tag/v2.55.0.windows.3) 公布值一致。本轮没有重新下载 ZIP，也没有据此声称对全部已解包文件逐字节复核。
2. 官方发行附件中找到了 [`mingw-w64-git-2.55.0.3-1.src.tar.gz`](https://github.com/git-for-windows/git/releases/download/v2.55.0.windows.3/mingw-w64-git-2.55.0.3-1.src.tar.gz)，大小 12,483,901 字节。官方 API 公布 SHA-256 `83fe0426914069810fe3b4b5b4c662f52757b553d05272933ca0ea370cf1d905`。这是上游公布值，本轮没有下载并计算该源码包的哈希、也未检查包内构建材料是否完整。
3. 本地 `resources/toolchains/mingit/etc/package-versions.txt` 与 [官方同版本清单](https://github.com/git-for-windows/git/releases/download/v2.55.0.windows.3/package-versions-2.55.0.3-MinGit.txt) 内容一致；本地哈希及官方公布值都是 `104ca60c3e0db5c282f92357fb99235e054d9c4105a0b8db1bd3d023cfbf6cbd`。该清单可能包含构建环境包，不能仅凭清单就认定每个包完整进入 MinGit；仍需映射实际文件。
4. Git for Windows 官方说明它由 MSYS2/MinGW 包的子集组成，源码和构建入口不止 Git 仓库本身，见 [技术概览](https://gitforwindows.org/technical-overview.html)。因此找到 Git 自身源码附件不能自动覆盖其他随带组件。
5. 本地 `LICENSE.txt` 的 GPL v2 第 3 条列出对应源码提供方式，并包含同一下载位置提供等价源码访问的情形。建议准备经过核验的对应源码及适用构建材料，和工作台发行物一起提供；不能仅写一句“开源所以免费”，也不应擅自作出尚无履约能力的三年书面承诺。具体义务以条款及实际分发方式复核。

本地 Linux 工具链仍是 `awaiting-verified-toolchain` 占位，只有 metadata/README，版本和许可路径为空。当前源码目录不能用于证明历史 Linux 发行包已经满足相同要求；需要对实际 Linux 产物另行核查。

## 发行范围与历史产物的额外发现

- **原生 Canvas 暂无分发证据**：主智能体使用 ASAR 文件目录 API 检查了当前 `release/win-unpacked/resources/app.asar` 的 8,548 个条目，未发现 `@napi-rs/canvas`、`canvas-win32` 或对应 Skia `.node` 路径；子智能体也检查了解包目录，未发现对应原生文件。本地 node_modules 中存在该可选开发依赖，不等于发行物携带它。这个结论只适用于本次本机产物，不保证未来所有构建都相同。
- **不能据此排除所有 Skia**：MinGit 中实际存在 `Avalonia.Skia.dll`、`SkiaSharp.dll` 和 `libSkiaSharp.dll`，这是另一条分发路径，需要结合 Git Credential Manager 的具体组件清单核查；不要混同于 npm Canvas。
- **SBOM 的范围需要进一步标清**：当前构建来源和传递依赖被统一标为 required。建议拆分为工作台实际运行文件、官方浏览器资源来源、仅构建期/可选依赖、工具链组件，避免把“构建目录里有”当成“已经随包分发”。本轮没有修改 SBOM 生成逻辑或删除依赖。
- **历史 alpha.26 仍有旧声明**：`release/win-unpacked/resources/room-modules/document.pdf.fontkit@1/LICENSE.txt` 仍是旧的 Andrew Dillon/pdf-lib 许可副本。当前源码生成目录已经改为 fontkit 自己的 `LICENSE-EVIDENCE.md` 和待核对 NOTICE，但未重新打包，因此不要用旧包代表此次许可证修订结果。

## 建议处理顺序

1. 优先处理明确随包的 fontkit、Git/MinGit 及 GCM 附加组件材料；解决后重新打包，验证最终 ZIP。
2. 对 AWS 三项完善原文来源与版本关联。类型声明明确不等于本轮已经取得全部适用声明。
3. 对其余旧包建立“最终文件／浏览器 bundle → 来源包”映射；只在确认不分发相应代码后，调整二进制发行范围，不随意删去构建来源记录。
4. 对确实随包、又无法获得清楚授权材料的部分，再决定联系上游、替换依赖或调整功能。改变功能或公开联系维护者需另行决定，本轮未执行。
