# 千万间 Roomillion v1 房间依赖打包策略

> 制定日期：`2026-08-30`
>
> 当前状态：策略与代码合同已在 `0.3.0-alpha.1` 开发版实现；官方模块目录在 v1.0 发布前仍可评审调整，v1.0 发布时冻结首个稳定基线。

## 1. 核心规则

房间依赖按以下顺序处理：

1. 如果工作台官方模块目录已经提供所需能力，房间只在 `hostModules` 中声明能力 ID，不把实现包复制进 `.room`。
2. 如果目录没有提供该依赖，打包器把实际使用的纯 Web 文件、许可证文件和元数据放进 `embedded/`，并登记到 `embeddedDependencies`。
3. 不允许把完整 `node_modules`、包管理器缓存、安装脚本、原生插件或动态下载器放进房间。
4. 运行时既不执行 `npm install`，也不从 CDN 补依赖；房间必须仅靠工作台共享资源和自身 `.room` 内容运行。

这与 Docker 镜像相似之处是产物可自包含；不同之处是千万间 Roomillion会优先去重官方公共层，并且房间只允许静态 Web 资源和窄 Room SDK。

## 2. 三类文件

| 类型 | 存放位置 | 是否进入 `.room` | 更新责任 |
|---|---|---:|---|
| 工作台官方模块 | 工作台 `resources/room-modules/` | 否 | 工作台统一更新并维持能力合同 |
| 房间额外依赖 | 房间 `embedded/<依赖-id>/` | 是 | 房间固定版本并随房间更新 |
| 房间自身代码与资源 | 房间 `app/` | 是 | 房间开发者/AI 维护 |

例如房间需要 CSV 和一个工作台未收录的 `tiny-helper@2.1.0`：

```text
example.room
├─ manifest.json                 # hostModules 声明 data.csv@1
├─ app/
│  ├─ index.html
│  └─ app.js
├─ embedded/
│  └─ npm.tiny-helper/
│     ├─ LICENSE.txt
│     └─ tiny-helper.min.js      # 只包含实际使用的浏览器资源
└─ integrity.json                # 同时覆盖 app 与 embedded 的 SHA-256
```

这个包里不会出现 Papa Parse；运行时由工作台通过 `data.csv@1` 提供。

## 3. Manifest 合同

```json
{
  "runtime": {
    "roomSdk": "1",
    "minimumWorkbench": "1.0.0"
  },
  "hostModules": [
    "data.csv@1"
  ],
  "embeddedDependencies": [
    {
      "id": "npm.tiny-helper",
      "package": "tiny-helper",
      "version": "2.1.0",
      "license": "MIT",
      "source": "npm:tiny-helper@2.1.0",
      "root": "embedded/npm.tiny-helper",
      "licenseFile": "embedded/npm.tiny-helper/LICENSE.txt",
      "files": [
        "embedded/npm.tiny-helper/LICENSE.txt",
        "embedded/npm.tiny-helper/tiny-helper.min.js"
      ],
      "entrypoints": [
        "embedded/npm.tiny-helper/tiny-helper.min.js"
      ]
    }
  ]
}
```

额外依赖必须满足：

- 精确语义化版本，不能使用 `^`、`~`、`latest` 或范围。
- 包名、来源和 SPDX 许可证/组织许可证引用必须明确。
- 许可证文件必须在该依赖的文件清单中。
- 所有入口必须同时列入 `files`，所有 `embedded/` 文件都必须恰好被一个依赖声明。
- `integrity.json` 对每个文件记录大小和 SHA-256；导入界面另外显示每个依赖的汇总体积和内容 SHA-256。
- 总包仍受 25 MB 压缩包、100 MB 解包后、500 个条目和跨平台原生载荷禁令约束。

## 4. v1.0 冻结与兼容

### 4.1 v1.0 首发基线

v1.0 发布时需要冻结“v1 基础官方模块目录”。所有合格的 v1.0 工作台发行物都必须自带这一基线，不能因便携版、安装版、Windows 或 Linux 而缺少其中一部分。

房间依赖的是 `data.csv@1` 这样的能力主版本，不依赖工作台内部具体使用 Papa Parse 的哪个补丁版本。工作台可以统一修复安全问题和替换内部实现，但同一 `@1` 合同必须兼容。

### 4.2 v1.x 新增能力

如果 v1.2 才新增某个官方模块，使用它的房间必须把 `minimumWorkbench` 提高到 `1.2.0`；不能假设旧 v1.0 已经拥有后来增加的资源。v1 基础目录则从 v1.0 开始始终存在。

### 4.3 旧房间兼容

某个包可能在旧房间中作为额外依赖存在，后来才进入官方目录。此时：

- 新建或重新编译的房间必须改用官方模块，打包器拒绝重复复制。
- 已经发布的旧 `.room` 仍允许导入、运行和原样重新导出，避免破坏历史产物。
- 导入界面会提示“该随房间依赖已可改用工作台共享模块”，供下一次开发迁移。

## 5. AI 与打包器的决策流程

```text
用户需求
  → AI 提取所需能力
  → 查询当前工作台官方模块目录
      ├─ 命中：记录 hostModules，不复制文件
      └─ 未命中：检查本地/内网依赖源
           → 固定版本与许可证
           → 只复制实际使用的浏览器资源
           → 写入 embeddedDependencies
  → 生成完整性清单
  → 可移植性、许可证和未声明文件检查
  → 生成 .room
```

当前结构化 AI 房间生成器只从官方目录选型，因此默认不会产生额外依赖。未来开放更自由的 Pi Coding Harness 时，必须调用同一个依赖打包器，不能让模型自行执行复制或 `npm install`。

## 6. 许可证与风险展示

打包器要求每个额外依赖携带许可证文本。当前工作台预审提示覆盖 MIT、Apache-2.0、BSD、ISC、0BSD、MPL-2.0、CC0 和 Unlicense 等常见许可；这只是自动风险分级，不代替法务结论。

- 有额外依赖：至少显示中风险提示，让用户知道代码不属于工作台官方公共层。
- 许可证不在预审集合：显示高风险提示，组织分发前必须复核。
- 包名后来对应官方模块：显示可迁移提示。
