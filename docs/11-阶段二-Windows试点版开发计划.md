# 千万间 Roomillion阶段二：Windows 试点版开发计划

> 实施进度：批次 A、B、C 以及批次 D 的代码和本机发行验收已于 `2026-08-28` 完成；干净机和 5～20 名内部用户试点仍待执行。证据见《13-0.2 阶段二实施记录》与《14-0.2 干净机试点验收手册》。

## 1. 阶段定位

阶段二的目标不是继续堆房间类型，而是把 `0.1.0` 从“本机可演示 MVP”推进为“可以交给第一批内网用户试用的 Windows 预览版 `0.2.0`”。

本阶段围绕五件事形成闭环：

1. 用户导入房间前能看懂来源、权限和风险。
2. 房间业务数据可以可靠备份、迁移和恢复。
3. AI 创建或修改房间时自动留下版本检查点，并能一键回退。
4. Windows 包内真正包含受控 MinGit，不依赖系统 Git 或 PATH。
5. AI API Key 可以安全记住，发行物在干净 Windows 电脑离线通过验收。

目标试点规模为 `5～20` 名内部用户。阶段结束前仍不对外宣称支持任意第三方恶意房间或所有 Linux 系统。

## 2. 本阶段范围

### 2.1 必须完成

| 能力 | 用户结果 | 验收摘要 |
|---|---|---|
| 导入预检 | 拖入 `.room` 后先看到名称、版本、来源、权限、完整性和风险提示 | 未确认前不安装、不授予权限 |
| 权限记录 | 权限按房间 ID、发布者和版本记录，可查看和撤销 | 新增权限必须再次确认，拒绝后对应 API 不可用 |
| 数据备份恢复 | 用户可导出密码保护的 `.zdata`，在另一台工作台恢复 | 错误密码、损坏包和房间 ID 不匹配均拒绝写入 |
| 自动安全备份 | 更新、恢复或回滚前自动创建本地检查点 | 失败后原数据库和程序仍可用 |
| 房间版本历史 | AI 生成和修改成功后自动提交检查点，用户可查看并回退 | 不显示 Git 命令，不要求用户理解分支 |
| 内置 MinGit | 固定路径调用包内 MinGit，隔离 HOME/config，禁用 hooks 和网络协议 | 删除系统 Git/PATH 后本地版本功能仍通过 |
| 密钥安全存储 | 用户可选择“记住密钥”，由 Electron 安全存储加密 | 配置文件和日志中不存在明文 Key |
| 试点诊断 | 一键导出脱敏诊断报告 | 默认不包含 API Key、业务数据或完整文件路径 |
| Windows 发行验收 | 便携版在干净 Windows x64 普通用户环境离线运行 | 无管理员权限、无开发工具、无外网也能完成本地闭环 |

### 2.2 本阶段不做

- UOS/Linux 正式发行、ARM64 和多发行版兼容承诺。
- 房间在线市场、自动下载依赖和自动更新。
- Git clone、fetch、pull、push 或任意 Git 终端。
- 任意 npm/Bun 后端、任意 Shell 和无限制本地文件访问。
- 公共 CA 代码签名证书采购；代码签名流程可准备，但证书采购是发布决策。
- 多人实时协作、云同步和组织后台。

UOS/Linux 技术验证作为阶段三入口；在 Windows 的包格式、权限和数据迁移仍变化时，不并行扩大认证面。

## 3. 关键用户流程

### 3.1 安全导入房间

```text
拖入 .room
  → 只读解包和完整性检查
  → 展示来源、版本、权限、风险和数据影响
  → 用户确认或取消
  → 保存授权记录
  → 原子安装并打开
```

来源状态首版分为：工作台内置、用户本机生成、已知发布者、未知/未签名。`0.2.0` 可以继续允许未知房间，但必须显示醒目提示，并且敏感权限默认不勾选。

### 3.2 备份和跨机器迁移数据

```text
选择房间
  → 设置备份密码
  → 工作台冻结短时写入并复制一致性数据库
  → scrypt 派生密钥 + AES-256-GCM 加密
  → 生成 .zdata
  → 另一台工作台验证、解密、预览并恢复
```

`.room` 继续只分享程序；`.zdata` 专门承载用户主动选择导出的数据，两者不能自动混装。

### 3.3 AI 修改与一键回退

```text
用户提出修改
  → 生成前创建检查点
  → AI 生成受约束定义
  → 校验、构建和自动测试
  → 成功后创建新检查点并安装
  → 用户可从“版本历史”恢复旧版本
```

Git 只是内部实现。界面使用“版本”“检查点”“恢复”这些业务语言，不暴露 commit、HEAD、rebase 等术语。

## 4. 技术方案

### 4.1 导入检查与权限账本

新增 `RoomInspector`，把导入拆成 `inspect → confirm → install`，不再由文件选择后直接安装。检查结果使用可序列化结构传给界面，至少包含：

- Manifest 基本信息和 SDK 兼容性。
- ZIP 路径、文件数、总体积和完整性结果。
- 权限的业务语言说明和风险等级。
- 已安装版本与待导入版本的权限差异。
- 来源/签名状态；未签名不等同于完整性失败。

新增独立权限账本，保存在用户数据目录而非房间包内。IPC 每次调用仍以运行时 Manifest 与用户授权的交集为准，不能只相信界面确认结果。

### 4.2 `.zdata` 数据包

定义格式版本 `0.1`，内容包括元数据、数据库快照、可选房间存储和完整性信息。跨机器备份默认要求密码：

- KDF：Node `crypto.scrypt`，参数随包记录并设置最低安全值。
- 加密：AES-256-GCM，每个包使用随机 salt 和 nonce。
- 恢复：先解密到临时目录，完成格式、哈希、房间 ID 和空间检查后再原子替换。
- 回滚：替换前自动保留本地快照；失败时恢复旧数据。

密钥、密码和解密内容不得写日志。大数据限制和错误提示要在实现时固定进规范与测试。

### 4.3 受控 MinGit 服务

MinGit 只服务于“房间源项目的本地版本历史”，不操作业务数据库。新增 `GitService`：

- 固定调用 `resources/toolchains/mingit/cmd/git.exe`，不搜索系统 PATH。
- 为每个房间使用独立项目目录和独立 Git 配置目录。
- 通过参数禁用 hooks、凭据助手、子模块、外部 diff、文件协议和网络代理继承。
- 仅暴露结构化操作：初始化、创建检查点、列出历史、查看摘要、恢复检查点。
- 所有提交使用工作台内部身份，不读取用户全局 Git 配置。
- MinGit 版本、下载来源、SHA-256 和许可证进入锁定清单与发行 SBOM。

包体会增大，但这是用户明确需要的离线版本能力；只在 `GitService` 和 UI 闭环同时完成后进入正式发行物。

### 4.4 AI 密钥和组织配置

使用 Electron `safeStorage` 对选择“记住”的 API Key 加密后落盘；Windows 下由当前用户的操作系统保护机制提供密钥保护。若当前环境不支持安全存储，则退回仅内存模式并明确提示，不能静默明文保存。

组织级 Provider 配置文件只能包含 URL、模型、显示名、代理/证书引用等非秘密信息。真实 API Key 由用户输入或后续组织密钥服务提供。

### 4.5 脱敏诊断

诊断包包含版本、平台、架构、房间清单摘要、错误类别和最近的脱敏事件。默认删除：

- API Key、Authorization Header 和用户输入的密码。
- 房间数据库、文件内容和 AI 对话正文。
- 用户名、绝对路径、内网主机名和 URL 查询参数。

导出前在界面展示将要包含的字段，用户确认后才写文件。

## 5. 实施批次

### 批次 A：导入预检和权限确认

任务：

- `P2-A01` 定义导入检查结果和权限业务文案。
- `P2-A02` 重构房间导入为只读预检与确认安装两阶段。
- `P2-A03` 实现权限账本、权限差异和撤销。
- `P2-A04` 增加导入确认页和房间详情页。
- `P2-A05` 增加 ZIP 炸弹、权限越权、取消安装和升级差异测试。

阶段门：未经确认不能安装；撤销文件/AI 权限后立即拒绝对应调用；数据库私有权限不能被关闭到破坏房间基本数据的状态。

### 批次 B：数据备份、恢复和回滚

任务：

- `P2-B01` 固化 `.zdata 0.1` 规范、限额和错误模型。
- `P2-B02` 实现一致性快照、密码加密、完整性检查和导出。
- `P2-B03` 实现恢复预检、自动备份、原子替换和失败回滚。
- `P2-B04` 增加备份/恢复 UI 与恢复历史。
- `P2-B05` 覆盖错误密码、篡改、磁盘空间不足和进程中断测试。

阶段门：在两套独立用户数据目录间完成跨机器等价恢复；任何失败不得覆盖原数据库。

### 批次 C：版本历史与 MinGit

任务：

- `P2-C01` 定义房间源项目目录和检查点元数据。
- `P2-C02` 实现结构化 `GitService` 及安全环境。
- `P2-C03` 获取并锁定 MinGit，记录哈希、许可证和 SBOM。
- `P2-C04` AI 生成/修改前后自动创建检查点。
- `P2-C05` 实现版本历史、变化摘要和一键恢复 UI。
- `P2-C06` 在移除系统 Git/PATH、无网络环境中完成测试。

阶段门：用户不接触命令行即可恢复旧版本；Git hooks、外部命令、网络协议和用户全局配置均不能被触发。

### 批次 D：密钥、诊断与试点发行

任务：

- `P2-D01` 用 `safeStorage` 实现可选的加密密钥持久化与清除。
- `P2-D02` 实现组织 Provider 非秘密配置导入。
- `P2-D03` 建立结构化脱敏日志和诊断导出。
- `P2-D04` 补充隐私、依赖许可证和 SBOM 文档。
- `P2-D05` 构建 `0.2.0` 便携版并执行干净机离线验收。
- `P2-D06` 用 5～20 名内部用户完成试点并收集任务成功率。

阶段门：静态扫描和人工检查均找不到明文 API Key；干净机无需管理员权限和开发工具即可完成全部本地验收场景。

## 6. 开发顺序和依赖

```text
A 导入/权限
  ├─→ B 数据备份/恢复
  └─→ C 版本历史/MinGit
          ↓
    D 密钥/诊断/试点发行
```

A 必须先做，因为 B 的恢复包和 C 的程序版本都会引入新的导入/恢复确认场景。B 与 C 在 A 的接口稳定后可以并行，但进入 D 前必须共同完成。

按单人连续开发估算为 `15～25` 个有效工作日，不包含代码签名证书采购和真实试点等待时间。每个批次单独可运行、可测试，不以“大版本最后一起联调”为前提。

## 8. 成功指标

试点期间至少记录：

- 首次成功启动率 ≥ `95%`。
- 不看开发文档完成示例房间安装的用户比例 ≥ `90%`。
- 数据备份并在另一环境恢复的成功率 ≥ `95%`。
- 从失败修改恢复旧版本的成功率为 `100%`。
- 因权限提示看不懂而放弃操作的比例 < `10%`。
- 任何明文密钥泄露、原数据被覆盖或权限绕过均为发布阻断问题。

## 9. 阶段结束后的决策点

`0.2.0` 试点结束后，依据真实设备和用户数据决定阶段三优先级：

1. 如果离线内网需求最强，优先做组织 Provider/证书配置和离线更新包。
2. 如果跨系统分享是试点的首要阻碍，锁定一款具体 UOS x64 版本做 Linux 目录包与 AppImage 技术验证。
3. 如果 AI 创建成功率是主要问题，优先扩展模板、评测集和受控编辑工具。
4. 如果分享范围扩大，优先建设发布者签名、组织信任库和房间审核流程。

阶段三只选择一个主目标，不同时启动“Linux、市场、任意代码、多用户协作”四条高成本路线。
