### 1.2 平台运行时、房间合同与 Git

- 新增 `win32-x64` 与 `linux-x64` 运行时描述；主进程不再硬编码 `git.exe`。
- Windows 固定使用包内 MinGit；Linux 固定使用 `resources/toolchains/git-linux-x64/bin/git`，绝不回退系统 Git。
- 两个平台均固定 Git executable、exec path、template path、库目录、空设备和路径分隔符；隔离 HOME、系统配置、hooks、凭据助手和网络协议。
- `.room` 打包和导入拒绝大小写/Unicode 冲突，以及 PE、ELF、Mach-O、`.dll`、`.so`、`.node` 等平台原生载荷；WebAssembly 仍可使用。
- `.zdata` 已覆盖两个独立数据根之间的等价迁移、认证篡改、磁盘不足和中断恢复。

### 1.3 Linux 工具链与构建链

- `collect-system-profile.sh` 生成不含主机名、用户名和网络地址的匿名画像，并记录 OS、内核、glibc、桌面会话、FUSE 2、用户命名空间和文件系统大小写能力。
- `prepare-git-toolchain.sh` 从当前 Linux 系统提取 Git、模板、非 glibc 动态库和许可证，生成元数据与 SHA-256，并在 `env -i` 下完成 init/add/commit/restore 冒烟；脚本不联网、不安装包、不要求 root。
- Linux Git 运行环境新增固定 `GIT_TEMPLATE_DIR`，消除对系统模板目录的隐式依赖。
- `bootstrap-build-runtime.sh` 固定 Node.js `24.20.0` Linux x64，并校验官方 SHA-256 `2f2c0da162318f0de47665410c7c8c2ed3d36c8f3105de4bbc61176c70a7cbf2`。
- `build-generic-preview.sh` 在 Linux 临时目录复制干净源码，只注入显式工具链；缓存统一位于项目 `.linux-build/`，支持 `--offline` 和 `--appimage`。
- 离线模式启用 `npm ci --offline`，并把 Electron 与 electron-builder 镜像固定到不可达本机端口；缓存缺失时构建会失败，不会联网补包。
- `verify-pilot.sh` 在普通用户、空 PATH 和离线审计下执行完整 Electron 冒烟；AppImage 缺少 FUSE 2 时临时解包运行，仍不使用 `--no-sandbox`。
- 冒烟报告可以持久保存，并包含房间运行、权限、备份恢复、内置 Git、诊断和零网络尝试的机器可读证据。

### 1.4 跨系统迁移与 UOS 验收包

- 新增 `migration-vector.cjs`：Windows 生成公开测试 `.room/.zdata`，记录文件哈希与业务行摘要；目标 Linux 恢复后写入第二条记录并回传；Windows 再次安装、恢复和核对。
- 迁移向量输入在安装前核对 SHA-256，回传必须绑定源向量；房间重新导出后的 SHA-256 必须保持一致。
- Linux 迁移使用发行物内置 Electron/Node 和 `app.asar` 中的 CLI，在空 PATH 下运行，不依赖系统 Node、Git 或网络。
- 新增 UOS 离线验收包：包含 `tar.xz`、AppImage、Windows 源向量、全包哈希、自动脚本、匿名画像工具、合规文件和 H02～H05 人工清单。

### 2.3 运行证据

## 3. 仍未完成，不能对外声称

- 尚未锁定具体统信 UOS 版本、补丁级别、桌面环境和设备型号。
- 尚未在目标 UOS 上重新制作并认证 Git 工具链；Ubuntu 24.04 的 glibc 基线不能自动代表 UOS。
- generic Windows → Linux → Windows 的真实包往返已完成；指定 UOS 上的同流程仍待执行。
- 尚未在目标 UOS 验证中文输入法、字体、高 DPI、拖放、文件选择、Chromium 沙箱、SQLite 文件锁、磁盘不足、内网 AI Provider 与私有 CA。
- 因此当前可以称为“generic Linux x64 技术预览”，不能称为“统信 UOS 已兼容版”或 `0.3.0` 正式版。

## 4. 目标 UOS 上的下一步

1. 将完整的 `UOS-x64-Acceptance-Kit.tar.xz` 复制到目标机，校验归档 SHA-256 后解压。
2. 使用普通用户在断网条件执行包内 `sh run-uos-acceptance.sh`；脚本会收集匿名画像、验证目录版/AppImage并生成 Linux 回传向量。
3. 完成结果目录中的 H02～H05 人工清单，补充截图和失败复现步骤。
4. 把整个结果目录复制回 Windows，运行 `npm run migration:verify-return`，归档 Windows 回迁报告。
5. 若目标机因 glibc/内置 Git ABI 失败，再在该 UOS 上运行工具链准备脚本并通过内网介质提供构建缓存，生成目标基线专用包；不得回退系统 Git。
6. 仅当画像、两种机器报告、迁移双端报告和人工清单全部通过，才评审该精确 UOS 版本的 `0.3.0` 发布资格。

## 5. 阶段判断

当前系统能完成的批次 E、F 和 generic G 研发工作已经闭环，并已具备可复制到内网/UOS 的无管理员构建与验收脚本。下一道不可替代的阶段门是取得一台精确版本的统信 UOS x64 设备并执行批次 H；当前 Windows 已推进到 `0.3.0-alpha.3`，Linux/UOS 发行物仍停留在 alpha.1，整体继续保持“技术预览、UOS 未认证”标识。

## 7. 2026-08-30 增量：房间依赖去重与随包策略

- 新房间使用工作台已提供包时只写 `hostModules`，打包器不复制实现文件。
- 目录外包必须以 `embeddedDependencies` 声明，并把精确版本、来源、许可证和实际使用的浏览器文件打入 `embedded/`；完整性清单覆盖全部文件。
- 未声明 `embedded/` 文件、整个 `node_modules`、浮动版本、缺少许可证、原生载荷和当前官方包的重复副本都会阻止新房间打包。
- 导入界面显示额外依赖的版本、许可证、文件数、体积和内容哈希；未预审许可证为高风险。
- 为兼容历史产物，旧房间若携带后来已内置的包仍可导入和重新导出，但会收到迁移提示。
- v1.0 发布时冻结基础官方模块目录；同一 `@1` 能力可由工作台统一修补内部实现，房间无需重打包。
- 新增依赖分层测试后 Windows 自动测试为 `61/61`；开发版、解包版和单文件便携版均实际预检 `tiny-helper@1.0.0`（MIT）测试依赖，显示内容哈希且网络尝试为 `0`。
