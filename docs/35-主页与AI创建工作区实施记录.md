# 主页与 AI 创建工作区实施记录

> 实施版本：0.3.0-alpha.13  
> 实施日期：2026-09-05

## 1. 用户现在看到什么

工作台启动后先进入“主页”。主页以卡片展示当前用户已经安装的全部房间，每张卡片包含房间名称、版本、来源信任状态和主要能力；点击卡片直接打开房间，右键仍可进入卸载菜单。

顶部标签栏现在统一管理三类工作区：

1. 固定的“主页”标签；
2. 按需出现的“AI 创建房间”标签；
3. 用户打开的普通房间标签。

AI 创建不再表现为覆盖房间的模态弹窗。它是与房间同级的完整工作区，会保留历史对话、当前会话、图片附件、工具时间线和模型状态。

## 2. 怎样使用独立 AI 窗口

- 点击 AI 标签上的 `↗`，或右上角窗口按钮，可把 AI 创建移到独立窗口。
- 把 AI 标签拖到主工作台窗口外，也会创建独立窗口；仍在主窗口范围内松开不会误弹出。
- 独立窗口中点击 `↙` 可主动收回。
- 点击操作系统关闭按钮时默认“收回工作台”，不会删除对话。
- 点击主工作台 AI 标签上的 `×` 才表示关闭这个工作区标签；历史会话仍保留在本地，重新进入可继续使用。

独立 AI 窗口使用与主工作台相同的安全 preload 和渲染页面，不启用 Node 集成，不允许任意导航或新窗口。

## 3. 多窗口同步

主工作台与 AI 独立窗口之间同步以下状态：

- AI 能力中心的当前提供商、模型和配置变更；
- Agent 新建、选中和更新的会话；
- 已安装房间列表及安装、更新、卸载变化；
- Agent 构建进度、工具调用和回复流；
- 独立/停靠窗口状态。

Agent 在独立窗口完成房间安装后，可从成果卡或主页卡片打开。工作台会聚焦主窗口、打开对应房间，并安全收回 AI 独立窗口。

## 4. 主要实现

- `src/main/agent-window-manager.cjs`：创建安全的 AI 独立 BrowserWindow，处理拖出、聚焦、收回、关闭和发送方身份。
- `src/main/ipc.cjs`：暴露 AI 工作区窗口命令，并把房间、模型和会话选择变化广播给两个工作台窗口。
- `src/preload/workbench-preload.cjs`：只暴露最小化、类型明确的 IPC 接口。
- `src/renderer/app.js`：实现主页、虚拟工作区标签、卡片入口、AI 停靠/独立状态和跨窗口会话同步。
- `test/agent-window-manager.test.cjs`：覆盖安全首选项、拖出边界、原生关闭归位和标签关闭。

## 6. 当前边界

第一版未实现把整个 AI 独立窗口拖回标签栏时自动吸附，也未实现一个窗口内组合多个独立标签。当前通过 `↗/↙`、拖出标签和关闭窗口归位完成可靠切换，不影响 Agent 会话连续性。

## 7. alpha.14 顶部拖动栏调整

工作台改用 38px 自定义顶部拖动栏，侧栏缩进按钮固定在最左端，并使用与 Codex 同类的分栏轮廓图标。原来位于房间标签工具栏左侧的按钮已经移除，避免标签起点随侧栏状态产生无意义偏移。按钮仍按“完整栏目 → 图标栏 → 完全收起 → 完整栏目”循环，状态继续保存在本机。

Windows 使用 Electron 原生标题栏覆盖区提供最小化、最大化和关闭控制；按钮和系统控制区标记为不可拖动，其余顶栏区域可拖动窗口。AI 独立窗口复用相同顶栏，但隐藏无意义的侧栏按钮并显示“AI 创建房间 · 千万间 Roomillion”。

## 8. alpha.15 多标签优化

标签栏改为浏览器式轨道。标签会在 `190px` 理想宽度与 `92px` 最小宽度之间自动收窄，标题过长时使用省略号；底层仍可横向滚动，但系统滚动条被隐藏。只有轨道确实溢出时才显示前后浏览按钮和“全部标签”菜单，菜单列出主页、AI 创建和所有已打开房间，并标记当前标签或独立窗口状态。

房间顶部仅保留“独立窗口”“AI 修改”“房间设置”三个高频操作；备份数据、恢复数据、导出房间和卸载房间进入“更多”菜单。此调整不改变权限判断和原有命令，只降低长期占用的横向空间。

## 9. alpha.16 窗口模式修正

顶栏从弹性并排改成 `minmax(0, 1fr) + auto` 的严格两列网格，标签轨道不能再用内容宽度把右侧操作区推离窗口。轨道内部也使用受约束网格，并通过 `ResizeObserver` 在窗口尺寸或控制区宽度变化后重新判断溢出。

当打开标签超过 5 个时，“全部标签”入口固定可见，即使特定缩放比例下浏览器的 `scrollWidth` 没有及时反映裁切，用户仍能访问所有房间。实际发生横向溢出时继续显示前后按钮，并支持在标签区域使用鼠标滚轮横向浏览。

左侧房间列表显式使用细滚动条：轨道透明，滑块默认弱化，悬停房间列表时显示半透明滑块，直接悬停滑块时再用品牌强调色显示。

## 10. alpha.17 房间运行时顶部菜单层级修复

普通房间由 Electron `WebContentsView` 承载，其原生视图层级高于工作台渲染页。alpha.16 的“全部标签”和“更多”菜单虽然已经在 DOM 中展开，但菜单超出顶栏的部分会落到房间视图后面，因此主页可用、进入房间后看起来无法点开。

alpha.17 在展开任一顶部下拉前临时从主窗口移除当前房间视图；关闭菜单、按 Esc、点击菜单外区域或窗口尺寸变化时，将同一个 WebContentsView 重新附着到同步后的房间视口。选择其他标签时直接交给原切换流程，不先恢复旧房间。整个过程不销毁 WebContents，所以房间页面、内存状态和数据库连接都不会因查看菜单而重载。

主程序强化冒烟新增了真实层级断言：房间内菜单展开时 `RoomViewManager.activeRoomId` 必须为空，菜单关闭后必须恢复为原房间 ID，同时检查菜单的 `hidden` 与 `aria-expanded` 状态。

## 11. alpha.18 AI 提供商与会话模型选择

AI 能力中心不再默认展开一个混杂的模型表单。首页只按 Provider 与服务地址显示“已连接提供商”，其下列出已启用模型、默认状态和编辑入口；点击“添加提供商”或“管理 / 添加模型”后才展开三步编辑区。

内置 Provider 的模型目录支持搜索、多选、全选未启用和清空，并显示上下文、推理、图片能力。已启用模型保持可见、标注且不可重复选择。同一 Provider 新增多个模型时，首个配置接收用户输入的 Key，后续配置只在主进程内通过来源配置 ID 复用凭据；页面和房间都拿不到 Key。

AI 创建房间顶部新增“编程模型”选择器。每个会话保存独立 `profileId`，切换后由 `RoomAgentService` 持久化，调用 `createAgentRuntime` 时显式路由到该配置；运行期间锁定选择器。模型被删除时会要求用户重新选择，不会静默把已有会话改成另一个模型。

alpha.18 自动测试为 `114/114`。源码和打包后 Electron 强化冒烟都实际验证 MiMo 两模型批量启用、凭据复用、默认项不变、已启用项锁定、房间多模型 API、9 个示例和 39 个模块；打包后离线审计结果为 `PASS`、普通互联网出站尝试 `0`、残留进程 `0`。

## 12. alpha.19 完整 Pi Provider 目录

AI 能力中心不再用人工白名单截取少量 Provider，而是每次启动都从锁定版本的 `@earendil-works/pi-ai` 读取完整原生目录。当前 Pi 0.84.3 注册 40 个 Provider，工作台再追加一个“自定义 / 内网 OpenAI-compatible”入口；界面按中国区与编程订阅、国际官方 API、聚合与推理平台、云平台、OAuth 与动态服务等类别分组，并支持按名称、ID、说明和类别搜索。

模型的协议与端点都以 Pi 模型记录为准。这样 OpenCode Zen 等同一 Provider 下同时包含 Anthropic、OpenAI Completions、Responses 协议和不同端点的模型，仍可复用同一份安全凭据。房间和 AI 创建会话继续只保存模型配置 ID，不获得 Key 或服务地址。

Kimi Code / Token Plan 与 Moonshot 开放平台现在是两个独立入口：

- `kimi-coding`：`https://api.kimi.com/coding`，Anthropic Messages，提供 `k3`、`k3-256k`、`kimi-for-coding`、`kimi-for-coding-highspeed`；
- `moonshotai-cn`：`https://api.moonshot.cn/v1`，OpenAI Completions，使用开放平台模型 ID。

当前 40 个 Pi 原生 Provider 中有 37 个具有 API Key 配置路径。OpenAI Codex 需要 OAuth、Radius 需要登录后动态刷新模型、Azure OpenAI 还需要资源地址和部署映射，这三个入口仍完整显示，但会禁用保存并说明所缺配置；Cloudflare、Vertex 和 Bedrock 的系统环境要求也会在界面提示。

alpha.19 新增完整目录、Kimi 分离、模型专属端点、跨协议凭据复用和限制状态测试，全量自动测试为 `117/117`；Electron 强化冒烟确认界面实际出现 40 个 Pi 原生 Provider、7 个分组和 1 个自定义入口。

## 13. alpha.20 Provider 选择器兼容性修复

Windows 上部分 Electron 环境无法可靠弹出原生 `select` 的系统下拉层，表现为点击“AI 提供商”没有反应。alpha.20 使用工作台自己的可展开目录替代可见原生下拉：整行按钮负责展开，目录按现有 7 个服务类别展示 Provider 卡片，搜索输入会自动展开过滤结果，选择后同步底层 Provider ID、更新摘要并自动收起。底层 `select` 仍作为唯一表单状态源并保持对既有保存逻辑和测试的兼容。

目录支持点击外部或 `Escape` 收起、上下方向键移动焦点；暂不能直接配置的 OAuth 或复合云 Provider 仍可被选中查看限制说明。Electron 冒烟测试新增真实的展开、41 项计数、Kimi 点击、标题同步和自动收起断言。

## 14. alpha.22 统一 `.room` 与可选密码

导出内容和安全保护改为两个互不依赖的维度：内容选择“只导出应用”或“应用和数据一起导出”，密码选择“设置”或“不设置”，因此共有四种有效组合，文件后缀全部统一为 `.room`。

- 仅应用、无密码继续生成原有标准房间 ZIP，保持对既有房间和其他工作台版本的兼容；
- 其余组合使用带清单的传输容器，应用和可选 SQLite 快照分别记录大小与 SHA-256；
- 设置密码时使用 scrypt + AES-256-GCM 加密整个传输载荷，导入者必须先解锁才能看到权限预检；
- 不设置密码且携带数据时，导入页明确提示数据未受密码保护，并在安装确认后进行 SQLite 完整性检查和原子恢复；

自动测试增至 `123/123`。源码和 alpha.22 打包版 Electron 冒烟均实际验证四组合界面状态、同后缀输出、错误密码拒绝、正确密码解锁、权限预检与暂存清理，结果为 `PASS`，离线审计普通互联网出站尝试为 `0`。

## 15. alpha.23 移除废弃双后缀兼容

房间导入只接受统一的 `.room`。主进程中的旧清单校验、旧完整包创建/检查、旧数据恢复适配、IPC 分流、渲染端二次密码流程、文件选择与拖拽旧后缀入口以及对应自动测试均已删除，不再保留兼容分支。独立的 `.zdata` 数据备份与恢复功能不受影响。

删除两项旧格式专项测试后，全量自动测试为 `121/121`；源码和 alpha.23 打包版 Electron 冒烟均为 `PASS`，统一 `.room` 的四种导出组合、错误密码拒绝、正确密码解锁、权限预检、数据恢复与暂存清理继续通过，离线审计普通互联网出站尝试为 `0`。源码全局扫描未发现废弃格式的标识符、后缀、界面状态或兼容分支残留。
