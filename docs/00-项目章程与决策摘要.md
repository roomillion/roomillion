# 千万间 Roomillion：项目章程与决策摘要

## 1. 文档目的

本文件用于发起项目、形成共同语言并约束早期范围。它说明为什么做、第一批为谁做、什么算成功，以及目前已经形成的核心决策。

## 2. 背景与问题

Vibe Coding 降低了写代码的门槛，却没有充分降低“把程序可靠交付给别人”的门槛。目标用户主要面临以下问题：

1. 不知道如何选择前端、后端、数据库和打包技术。
2. 静态网页容易分享，但涉及本地文件、数据库或 AI 的程序难以交付。
3. npm、GitHub 和其他包源在国内网络或隔离内网中不可用。
4. 内网虽然可能部署本地 AI，却无法即时下载开发依赖。
5. Windows 与统信/UOS 等 Linux 环境的可执行程序和依赖不同。
6. 传统开发工具、终端、环境变量和管理员权限对非程序员不友好。
7. AI 生成的任意代码拥有过大系统权限，导入他人项目存在安全风险。

这些问题不是单纯增加一个代码生成界面就能解决的，需要同时约束生成格式、运行能力、依赖来源和分发方式。

## 3. 产品定位

千万间 Roomillion 是一个离线优先、跨平台、面向非程序员的受控 Vibe Coding 平台。

- AI 生成的程序称为“房间”。
- 房间不是独立安装的软件，而是运行在工作台中的标准化应用包。
- 房间使用工作台提供的数据库、文件、AI、导入导出等能力。
- 房间可以导出为单个 `.room` 文件并分享。
- 同一个房间文件应能在受支持平台的工作台中运行。
- 工作台本体自带所需运行时和工具，运行时不在线安装依赖。

产品形态更接近“桌面小程序平台”，而不是缩小版 Docker，也不是可以生成任意技术栈的通用 IDE。

## 4. 目标用户

### 4.1 业务创建者

不会或不愿管理开发环境，希望用自然语言制作台账、表单、分析、文档和自动化小工具。

### 4.2 房间使用者

收到同事分享的房间后，希望拖入即可使用，不关心它由什么语言、框架或数据库实现。

### 4.3 内网管理员

需要控制 AI 服务地址、网络访问、可用组件、房间签名和数据边界。

### 4.4 高级开发者

需要制作官方模板、Room SDK 组件或经过审核的扩展能力，但不是 MVP 的主要交互对象。

## 5. 核心价值主张

1. **不再选技术栈**：AI 只能在固定房间标准内开发。
2. **分享即使用**：程序与用户数据分离，房间文件可拖入工作台运行。
3. **离线可用**：工作台自带 Electron/Chromium、Pi、Bun、Git、SQLite 和标准组件。
4. **跨平台房间**：平台差异由工作台吸收，房间不携带平台专属可执行文件。
5. **能力可控**：文件、数据库、AI 和网络都通过权限化 Room SDK 提供。
6. **AI 接入统一**：通过 Pi 的 Provider 能力连接云端、国内厂商和内网兼容接口。

## 6. 已形成的关键决策

| 编号 | 决策 | 状态 |
|---|---|---|
| D-001 | 房间采用小程序式受控运行模型，不是任意代码容器 | 已接受 |
| D-002 | 房间的常见“后端能力”由工作台统一提供，不为每个房间启动 Web 服务器 | 已接受 |
| D-003 | Bun 用于脚手架、构建、检查、测试和打包，不作为房间安全边界 | 已接受 |
| D-004 | Pi 通过适配层接入，复用多 Provider 和 Agent 能力，不向模型直接开放无限制 Shell | 已接受 |
| D-005 | 房间程序与用户数据分离，普通分享默认不包含用户数据 | 已接受 |
| D-006 | 工作台提供无管理员权限的用户安装版和便携版 | 已接受 |
| D-007 | Windows 内嵌 MinGit；Linux 打包目标平台对应的 Git | 原则接受，待验证 |
| D-008 | 第一版优先评估 Electron，以自带 Chromium 换取页面一致性 | 候选方案，待阶段 0 验证 |
| D-009 | 网络默认关闭，AI 调用只经过工作台 AI Gateway | 已接受 |

详细理由及可替代方案见 [07-风险与决策记录](07-风险与决策记录.md)。

## 7. MVP 范围

MVP 必须形成以下闭环：

1. 用户用自然语言创建一个房间。
2. AI 在受限工程目录内生成和修改代码。
3. 工作台可以构建、验证和预览房间。
4. 房间可以使用独立 SQLite、私有文件和用户授权文件。
5. 房间可以通过 AI Gateway 调用用户配置的模型。
6. 房间可以导出成单个 `.room` 文件。
7. 另一台受支持设备可以离线导入并运行该房间。
8. 工作台具备无管理员用户安装版及便携版。

## 8. MVP 明确不做

- 生成任意 Python、Java、C++ 或原生桌面程序。
- 允许房间安装任意 npm 包或执行任意系统命令。
- 承诺支持所有 Linux 发行版和所有国产 CPU。
- 多机同时写入同一个 SQLite 文件。
- 房间直接读取 API Key。
- 公共房间市场、在线支付和社交系统。
- 复杂多人实时协作。
- 默认把大模型权重打进工作台安装包。

## 9. 成功标准

### 技术验证成功

- 一台完全离线的目标机器可以安装或便携运行工作台。
- 同一个示例房间在 Windows x64 和指定 UOS x64 环境运行。
- 房间没有直接 Node、Git、Bun 和任意文件系统权限。
- 房间能通过授权完成 SQLite、文件选择和 AI 流式调用。

### MVP 成功

- 新用户在无命令行操作的情况下完成“描述需求—生成—修改—导出—另一台机器导入”的全过程。
- 10 个代表性房间模板均可离线运行。
- 房间更新不破坏既有用户数据。
- 导入篡改包会被完整性检查阻止或明确警告。
- 关键操作具备可诊断日志，且日志不泄露 API Key。

### 试点成功

- 至少一个真实业务部门持续使用，而不是只完成演示。
- 非开发用户可以独立创建或修改简单房间。
- 管理员能够离线下发 AI Provider、证书、房间和工作台更新。

## 10. 项目原则

1. 工作台可以大，房间必须小。
2. 将兼容性放在宿主，将业务逻辑放在房间。
3. 默认拒绝，按能力授权。
4. 运行时不下载依赖。
5. 先保证可迁移的数据，再考虑炫目的生成体验。
6. AI 是房间开发者，不是系统管理员。
7. 用可验证的支持矩阵替代“理论上跨平台”。
