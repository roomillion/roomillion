# 千万间 Roomillion风险与决策记录

## 1. 使用方法

本文件同时维护重大风险和架构决策。决策一旦被接受，不通过新 ADR 直接推翻；风险每个里程碑至少复审一次。

决策状态：`提议 / 已接受 / 已替代 / 已拒绝`。

## 2. 架构决策记录

### ADR-001：采用房间平台，而不是任意技术栈容器

- 状态：已接受
- 决定：AI 只能生成符合 Room SDK 和 `.room` 规范的应用。
- 理由：消除技术选型、运行依赖和跨平台分发差异。
- 代价：不能承载任意现有项目，生态范围受限。
- 复审条件：真实试点中大多数核心场景无法由 Room SDK 表达。

### ADR-002：常用后端能力由工作台托管

- 状态：已接受
- 决定：房间不启动独立 Web 服务，通过 Capability Broker 使用 SQLite、文件、AI 和任务。
- 理由：避免端口、进程、权限和依赖问题。
- 代价：宿主 API 设计和兼容责任增加。
- 复审条件：出现无法通过结构化任务或 WASM 承载的高价值场景。

### ADR-003：Bun 是构建工具，不是房间安全边界

- 状态：已接受
- 决定：Bun 随工作台打包，用于脚手架、构建、检查和测试；房间不以 Bun 可执行程序形式分发。
- 理由：Bun 单机开发效率高，但目标平台可执行文件并非通用房间格式，任意 Bun 代码也拥有过大宿主权限。
- 代价：需要独立设计房间运行时和 Capability Broker。

### ADR-004：通过适配层集成 Pi

- 状态：已接受
- 决定：工作台维护 `PiAdapter` 和稳定 Provider 配置，不深度耦合 Pi CLI 配置与默认工具。
- 理由：复用多 AI API、会话和 Agent 循环，同时控制升级和权限。
- 代价：需要维护一层转换和兼容测试。

### ADR-005：第一版优先验证 Electron

- 状态：提议
- 决定：使用 Electron 提供自带 Chromium 的桌面外壳。
- 理由：页面表现一致，避免依赖目标 Linux 的 WebKitGTK 版本；Electron 自带 Node 可承载 Pi SDK。
- 代价：包体和内存较大，Linux 基础库及沙箱仍需认证。
- 接受条件：阶段 0 在指定 UOS 上通过启动、中文输入、文件、沙箱和便携分发测试。
- 替代方案：Tauri/Wry、CEF 或平台专用外壳。

### ADR-006：程序与数据分离

- 状态：已接受
- 决定：`.room` 默认只携带程序；数据库、文件和权限由工作台独立保存。
- 理由：分享安全、更新可回滚、避免意外泄露数据。
- 代价：需要独立数据快照和迁移设计。

### ADR-007：工作台内嵌 Git

- 状态：原则已接受
- 决定：Windows 使用 MinGit 候选，Linux 使用目标平台 Git；不依赖系统 PATH。
- 理由：离线可用和行为可重复。
- 代价：增加包体、许可证和安全更新责任。
- 接受条件：阶段 0 验证所需 Git 功能、SSH/证书需求和目标平台兼容。

### ADR-008：网络默认关闭，AI 经过 Gateway

- 状态：已接受
- 决定：房间默认无任意网络；AI 由工作台统一连接 Provider。
- 理由：保护密钥、便于内网策略、审计和配额。
- 代价：所有 AI 协议兼容问题集中到工作台。

### ADR-009：无管理员安装和便携版同等重要

- 状态：已接受
- 决定：Windows 同时发布 per-user 安装版与 Portable ZIP；UOS/Linux 发布 AppImage 候选和目录版兜底。
- 理由：覆盖严格内网、临时设备和普通用户权限场景。
- 代价：发布和测试矩阵扩大，凭据存储需双模式设计。

### ADR-010：提供商连接与模型选择分层

- 状态：已接受
- 背景：一个 Provider 往往提供多个模型。把每个模型都显示成独立连接会让用户分不清“已连接”和“可导入”，也会造成重复填写 Key。
- 决定：AI 能力中心按 Provider 与服务地址展示连接，在连接下展示已启用模型；同一连接可批量启用模型并在主进程复用凭据。AI 开发会话和房间只保存脱敏的模型配置 ID，不保存 Key 或服务地址。
- 理由：匹配用户对“先连接账号、再选模型”的直觉；支持不同开发会话和不同房间独立选模型；保持 Gateway 的密钥隔离。
- 代价：同一凭据会为每个已启用模型维护独立的会话/加密副本；Provider 模型目录更新时需要处理已下架模型。
- 替代方案：每个模型独立填写连接；只保留一个全局模型；房间自行配置 Key。三者分别带来重复配置、无法并行选型或密钥暴露，因此不采用。
- 生效范围：`0.3.0-alpha.18` 起的 AI 能力中心、Pi Agent 会话、`window.room.ai` 文档和验收。
- 复审条件：Provider 引入 OAuth 账号授权、动态远端模型发现或组织集中密钥托管时重新评估连接实体。

### ADR-011：Provider 目录以 Pi 原生目录为唯一来源

- 状态：已接受
- 背景：工作台曾用 11 项人工白名单展示 Provider，导致 Pi 已支持的 Kimi Code 等入口不可选，并可能把订阅 Key 错配到 Moonshot 开放平台。
- 决定：工作台动态读取锁定 Pi 版本的全部原生 Provider 与模型，不复制模型清单；展示鉴权方式、模型专属端点和当前工作台配置限制。自定义内网入口仍作为工作台扩展保留。
- 理由：减少目录漂移和错误端点；Pi 升级后的 Provider/模型变化可由契约测试直接发现；AI 创建和房间 AI 可以共享相同的完整模型池。
- 代价：目录数据量增大；OAuth、动态目录和云厂商复合凭据需要继续扩展工作台的安全凭据界面。
- 生效范围：`0.3.0-alpha.19` 起的 AI 能力中心、主工作台 AI 服务与房间模型选择接口。

## 3. 重大风险台账

| 编号 | 风险 | 概率/影响 | 缓解措施 | 触发或验证点 |
|---|---|---|---|---|
| R-01 | Electron 在目标 UOS 的基础库、输入法或沙箱不兼容 | 高/高 | 锁定具体系统；阶段 0 实机验证；保留目录包和替代外壳评估 | 阶段 0 |
| R-02 | 房间或 AI 生成代码逃逸到宿主权限 | 中/极高 | Node 关闭、进程沙箱、窄 IPC、签名、受控 Agent 工具、威胁建模 | 原型及每次安全评审 |
| R-03 | Pi 升级造成 Provider 或 SDK 破坏 | 中/中 | PiAdapter、锁定版本、契约测试、离线升级包 | 每次 Pi 升级 |
| R-04 | OpenAI-compatible 厂商实际协议不兼容 | 高/中 | Provider 兼容档案、连接测试、能力检测、错误分类 | AI Gateway 原型 |
| R-05 | 本地小模型无法稳定生成符合规范的房间 | 高/高 | 固定模板、较少 API、SDK 检索、构建反馈、参考任务评测 | 阶段 2 前 |
| R-06 | 内置 Electron+Bun+Git 导致包体过大 | 高/中 | 接受“宿主大、房间小”；压缩；按架构发行；测量启动和升级成本 | 阶段 0/发布评审 |
| R-07 | 便携版 API Key 随 U 盘泄露 | 中/高 | 默认不保存或主密码保险库；明确便携/本机凭据模式 | AI 能力中心设计评审 |
| R-08 | 房间升级破坏 SQLite 数据 | 中/高 | 程序数据分离、事务迁移、升级前备份、故障注入测试 | 阶段 1 |
| R-09 | Git 或导入仓库触发 hooks/协议漏洞 | 中/高 | MinGit、禁用 hooks/子模块/危险协议、结构化 Git 工具、安全更新 | Git 集成评审 |
| R-10 | 第三方许可证不允许预期的分发方式 | 低/高 | 早期许可证清单、法务复核、随包提供声明和源码义务材料 | 阶段 0/正式发布前 |
| R-11 | “跨平台”宣传超过已验证范围 | 高/中 | 公布认证矩阵；同房间跨平台与工作台二进制分开说明 | 每次发布 |
| R-12 | 内网私有 CA、代理或 TLS 导致 AI API 不可达 | 高/中 | Provider 级代理、证书配置、诊断测试、管理员模板 | 阶段 2/试点 |
| R-13 | 共享资源升级破坏旧房间 | 中/高 | 主版本 API、兼容窗口、模块契约测试、明确淘汰政策 | SDK 设计评审 |
| R-14 | 需求扩张为通用 IDE/容器，失去产品边界 | 高/高 | 以 MVP 非目标和 ADR-001 为准；新增语言/运行时必须单独立项 | 每次范围评审 |
| R-15 | 未签名的单文件自解压程序被安全软件误报或隔离 | 高/高 | 正式代码签名；向安全厂商提交误报；发布带哈希的 ZIP 目录便携版兜底；不得要求用户关闭杀毒软件 | 每次 Windows 发布 |

## 5. 决策变更模板

新增 ADR 时使用：

```text
### ADR-XXX：标题

- 状态：提议
- 背景：为什么现在必须决定
- 决定：选择什么
- 理由：关键证据
- 代价：接受哪些缺点
- 替代方案：评估过什么
- 生效范围：影响哪些版本和文档
- 复审条件：出现什么证据时重新考虑
```

## 6. 每次里程碑风险复审

1. 是否出现新的高影响权限或供应链风险？
2. 是否有已知漏洞但内网用户无法及时更新？
3. 认证支持矩阵是否与宣传一致？
4. Pi、Electron、Bun、Git、SQLite 是否仍处于受支持版本？
5. 是否有房间无法迁移或数据无法恢复？
6. 是否有用户为绕过限制而使用不受控脚本或外部工具？
7. 哪个风险已经不再成立，哪个缓解措施没有实际效果？
