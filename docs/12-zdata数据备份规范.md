# 千万间 Roomillion `.zdata` 数据备份规范 0.1

## 1. 定位

`.room` 只携带房间程序，`.zdata` 只携带用户主动导出的房间业务数据。两者分离，避免分享模板时意外带出真实数据。

当前 `0.1` 备份格式只包含每房间的 SQLite 数据库。Room Storage 位于同一数据库的 `__room_kv` 表，因此随数据库一并备份；房间程序、权限账本、API Key、Git 历史和工作台配置不进入 `.zdata`。

## 2. 外层结构

文件使用 UTF-8 JSON：

```json
{
  "kind": "zhibian-room-data",
  "formatVersion": "0.1",
  "room": { "id": "cn.example.room", "name": "示例", "version": "1.0.0" },
  "createdAt": "2026-08-28T00:00:00.000Z",
  "encryption": {
    "kdf": "scrypt",
    "cipher": "aes-256-gcm",
    "N": 16384,
    "r": 8,
    "p": 1,
    "salt": "base64",
    "iv": "base64",
    "tag": "base64"
  },
  "payload": "base64 ciphertext"
}
```

房间 ID、名称、版本、创建时间和加密参数可见，但全部作为 AES-GCM AAD 参与认证，不能在不破坏认证标签的情况下被替换。

## 3. 加密载荷

解密后的 JSON 包含：格式版本、房间 ID/版本、数据库字节数、数据库 SHA-256 和数据库 Base64。密码要求为 8～128 个字符。

- KDF：scrypt，`N=16384`、`r=8`、`p=1`，随机 16 字节 salt。
- 加密：AES-256-GCM，随机 12 字节 IV、16 字节认证标签。
- 数据库与 `.zdata` 不再设置人为产品体积上限，以磁盘空间和当前 Node Buffer 可寻址范围为准。导出过程分段写入，恢复仍会做大小、哈希和 SQLite 完整性校验。

实现不得记录密码、派生密钥、明文载荷或数据库内容。

## 4. 恢复顺序

1. 限制文件类型和大小，解析外层结构。
2. 验证备份房间 ID 与当前房间一致。
3. 用用户密码派生密钥并验证 AES-GCM。
4. 验证内部房间 ID、数据库字节数和 SHA-256。
5. 用独立 sql.js 实例执行 `PRAGMA integrity_check`。
6. 持久化当前活动数据库并关闭内存实例。
7. 把当前 `room.db` 复制到本地恢复点目录。
8. 通过同目录临时文件和重命名替换数据库；失败时恢复旧文件。
9. 每房间最多保留最近 5 个恢复前检查点。

错误密码、篡改、格式错误、房间不匹配或 SQLite 损坏都必须在替换前失败。

## 5. 兼容规则

- 未识别的 `formatVersion` 必须拒绝，不能猜测兼容。
- 恢复数据不改变房间程序版本、权限和版本历史。
- 新版工作台增加载荷类型时应升级格式版本或增加明确的可选字段，不得改变 `0.1` 字段含义。
