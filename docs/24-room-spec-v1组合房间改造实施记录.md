# room-spec@1 组合房间改造实施记录

> 实施日期：2026-09-01
> 状态：第一版已实现，并通过单元、打包、Electron 离线和真实 MiMo v2.5 验收

## 1. 解决了什么问题

此前普通 AI 创建房间只生成“名称、说明、字段、模块”JSON，工作台始终套用同一套台账 HTML 和 JavaScript；3D 路由也只是固定收集游戏的参数化版本。因此两个需求即使差异很大，最终仍像同一个程序。

本次把新的普通 AI 创建流程切换到版本化的 room-spec@1：

- AI 设计完整页面、组件、数据源、字段、动作和受控计算表达式。
- 工作台严格校验规格，并编译出与需求对应的 HTML 结构。
- 运行时提供数据库、渲染、动作、图表、搜索、计算和导出等确定性能力。
- AI 返回的文本不会作为 JavaScript 执行。
- 旧台账房间和现有 3D 房间继续按原格式加载、修改和分享。

这不是任意代码生成器，而是第一版“组件 DSL + 行为 DSL + 受控表达式”编译器。

## 2. 第一版能力边界

### 2.1 页面与布局

- 一个房间可有 1～6 个页面。
- 页面可以使用纵向堆叠或 1～3 列网格。
- 多页面由房间顶部标签切换；页面结构会直接编译进各房间的 index.html。

### 2.2 组件

| 组件 | 用途 | 主要行为 |
|---|---|---|
| hero | 欢迎区、业务标题 | 标题、说明、徽标 |
| text | 说明和帮助 | 纯文本或经过 DOMPurify 清理的 Markdown |
| stats | 关键指标 | 记录数、合计、平均、最小、最大 |
| form | 数据录入 | 类型化字段、必填校验、保存到私有 SQLite |
| table | 明细列表 | 字段列、搜索、受控行操作 |
| cards | 卡片列表 | 卡片展示、搜索、受控行操作 |
| board | 状态看板 | 按 select 字段分栏，并可在栏间改变状态 |
| chart | 数据图表 | 柱状、折线、环形；计数、合计、平均 |
| calculator | 即时测算工具 | 数值输入和受控表达式输出，不需要数据库 |
| export | 数据导出 | XLSX、CSV、JSON |

### 2.3 数据与动作

- 一个房间可声明 0～4 个数据源，每个数据源 1～16 个字段。
- 字段类型为 text、textarea、number、date、select、boolean。
- 记录统一保存在房间自己的 __zhibian_records 表中，并以稳定数据源 ID 隔离。
- 动作只允许 set-field、toggle、delete，必须引用已声明的数据源和字段。
- 计算表达式只允许数字、输入引用和 add/subtract/multiply/divide/percent/min/max，不使用 eval 或 Function。

## 3. AI Harness

新建普通房间的流水线为：

1. Pi AI Provider 接收用户需求，要求返回完整 room-spec@1 JSON。
2. 本地验证版本、ID、引用关系、数量上限、字段类型、动作和表达式树。
3. 本地根据原需求补齐可确定的搜索、图表、统计和导出组件。
4. 根据最终组件和字段确定性选择内置模块，不让模型决定 npm 包：
   - 日期字段 → data.date@1
   - 数值、统计和计算器 → data.decimal@1
   - 搜索 → data.search@1
   - 图表 → ui.chart@1
   - Markdown → document.markdown@1 及安全清理依赖
   - XLSX/CSV 导出 → 对应电子表格和 CSV 模块
5. 质量门禁核对用户明确要求的仪表盘、图表、计算器、看板、录入、搜索、导出和多页面。
6. 首次失败时，同一次操作最多进行一次 JSON 修复；两次都失败则不安装半成品。
7. 编译 HTML、CSS、规格文件和受控运行时，打包并安装 .room。
8. 内置 MinGit 在创建后和每次修改前后建立检查点。

AI 修改组合房间时必须返回完整新规格。只要保留数据源 ID，已存业务记录继续可用；如果新增权限，仍按权限账本处理。

## 4. 打包与离线规则

- 组合房间的 manifest.json 只声明实际需要的官方模块。
- 官方模块资源由工作台共享，.room 不重复打包。
- embeddedDependencies 固定为空；当前 AI 组合房间不引入目录外包。
- permissions.network 固定为空。
- 没有数据源的纯计算器不申请数据库权限。
- 只有包含导出组件时才申请文件导出权限。
- CSP 保持禁止 JavaScript unsafe-eval 和外部连接。

## 5. 兼容策略

| 房间类型 | 定义文件 | 当前处理 |
|---|---|---|
| 旧结构化台账 | window.ROOM_DEFINITION | 继续加载和 AI 修改 |
| 组合房间 | window.ROOM_SPEC | 使用 room-spec@1 编译与修改 |
| 受控 3D 游戏 | window.GAME_DEFINITION | 继续使用第一版 3D 路由 |

安装和更新仍使用原 .room 0.1 包合同，所以分享、完整性校验、权限预检和跨平台机制不需要改变。

## 7. 当前限制与下一步

第一版仍不允许 AI 输出任意房间 JavaScript。尚未覆盖审批节点编排、多个数据源关联查询、文件导入处理、PDF/Word/PPT 组件、超长文本组件、复杂公式条件和自定义 2D/3D 场景。

推荐下一步按以下顺序扩展：

1. 建立 30～50 条需求金标集，统计 room-spec 首次通过率和需求覆盖率。
2. 增加 file-import、large-text、document-preview、document-generate 等受控组件，让现有办公与超长文本模块能被新编译器直接选用。
3. 增加数据源关联、筛选器和审批工作流动作。
4. 在 DSL 表达力仍不足的场景引入受限房间代码兜底；在此之前完成静态审计、能力调用白名单和更细的 CSP/权限模型。
5. 冻结 room-spec@1 后再定义升级和迁移规则，避免开发期规格成为长期兼容负担。
