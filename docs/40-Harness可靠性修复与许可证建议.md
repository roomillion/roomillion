## MIT 还是 Apache-2.0

**推荐 Apache-2.0 用于你拥有权利的工作台原创代码**。两者均为宽松许可证，允许商用、修改和分发；MIT 更简洁，Apache-2.0 对贡献者专利授权、专利诉讼终止条件及贡献提交约定写得更明确。对于准备长期维护、接受贡献和企业集成的工作台，我倾向 Apache-2.0，而不是因为它能替代第三方许可审查。[Apache-2.0 原文](https://www.apache.org/licenses/LICENSE-2.0)、[MIT 原文](https://opensource.org/license/mit)

Apache-2.0 的专利授权限于贡献者可授权且落入条款范围的专利，不是“无专利风险”保证。两者也都不能帮助重新授权你无权授权的代码或第三方素材。本建议是工程合规准备，不是正式法律意见。

选择尚未定稿，因此本轮没有添加根 LICENSE、没有修改现有 MIT 模块的许可证，也没有声称整个安装包均采用 Apache-2.0。确认后应补完整 LICENSE、正确版权主体、package.json SPDX 标识与 README 授权范围；打包白名单也须纳入这些文件。

## 引用的包要不要声明？要，且继续适用各自许可证

不能只在 README 写“使用了一些开源库”，也不能把整个依赖目录统一改成 Apache-2.0。

| 类型 | 项目中的例子 | 应随分发保留的主要材料 |
| --- | --- | --- |
| MIT | Pi Agent/Pi AI、Three.js、ExcelJS、sql.js | 原版权声明和 MIT 许可文本；不能只写许可证名称 |
| Apache-2.0 | PDF.js、SheetJS、Rapier、ECharts、mathjs | 完整许可；保留适用的版权/归属信息；上游有 NOTICE 时保留适用内容；修改上游文件时标示修改 |
| BSD / ISC | Mammoth、Leaflet、Quill、D3 等 | 对应许可文本、版权、免责声明；具体以每个包条款为准 |
| OFL-1.1 | Noto CJK 字体 | 字体版权与 OFL 文本；修改字体时另查保留字体名称等条件，不用主项目许可证替换字体许可 |
| GPL-2.0 及工具链其他许可 | MinGit/Git 与随带组件 | 保留原许可，按实际分发方式落实对应源码等要求；MinGit 中的每个组件还需分别核对 |

MIT 与 Apache 的上述义务可直接查阅其原文；字体条款见 [OFL 官方文本](https://openfontlicense.org/open-font-license-official-text/)。MinGit 自带 `resources/toolchains/mingit/LICENSE.txt` 明确以 GPL v2 为基准，并在第 3 条规定二进制分发时的源码提供方式。不能把一个 GitHub 下载链接未经复核就当作已经履行全部源码义务。

目前 Git 是独立子进程工具，房间不能直接访问它。独立聚合不应简单等同于将 GPL 代码链接进工作台，但是否构成独立聚合、源码如何提供及其他随包 DLL 的义务，正式公开前仍应复核。Apache-2.0 与 GPL-2.0-only 代码合并不是可以忽略的兼容性问题。
