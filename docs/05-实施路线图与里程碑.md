# 千万间 Roomillion实施路线图与里程碑

## 1. 路线图原则

项目最大的风险不是界面能否做出来，而是房间边界、安全模型、UOS 兼容、离线构建和升级数据能否同时成立。因此采用阶段门管理：每一阶段都有明确产物和退出条件，退出条件未满足时不扩大功能范围。

以下时间仅作为 4～6 人核心团队的建议量级，实际计划应根据目标系统、试点资源和安全要求调整。

## 2. 阶段总览

| 阶段 | 建议量级 | 目标 | 关键退出条件 |
|---|---:|---|---|
| 0. 需求锁定与技术探针 | 2～3 周 | 验证最大技术假设 | Windows/UOS 上跑通最小房间和离线运行时 |
| 1. 房间运行时原型 | 4～6 周 | 形成导入、运行、数据和权限闭环 | 同一房间跨两平台，无法直接访问宿主特权 |
| 2. AI 创建 MVP | 8～12 周 | 形成自然语言创建、构建、修改、导出闭环 | 非开发用户完成 5 个验收场景 |
| 3. 内网试点版 | 6～10 周 | 完成分发、安全、诊断和真实业务试点 | 一个业务部门持续使用并完成管理员部署 |
| 4. 产品化与生态 | 持续 | 扩展模板、组织能力、签名和升级体系 | 依据试点数据逐项立项 |

## 3. 阶段 0：需求锁定与技术探针

### 目标

在投入完整 UI 和 Agent 体验前，证明关键基础可以成立。

### 必做事项

1. 确定第一批 Windows 和 UOS 的确切版本及 CPU。
2. 选定三个真实业务样例和一批目标用户。
3. 建立最小 Electron 外壳，打开两个隔离房间。
4. 从 `.room` 导入静态房间并验证安全解包。
5. 通过 Capability Broker 完成 SQLite、选择文件和导出。
6. 在 Electron Node 环境嵌入 Pi SDK，并接入一个公网和一个内网兼容 API。
7. 从应用资源目录调用内置 Bun 和 MinGit/目标 Git。
8. 制作 Windows 免管理员便携包和 UOS 目录包。
9. 记录内存、启动时间、包体、兼容问题和安全缺口。

### 退出条件

- 同一房间在两个目标平台使用同一包运行。
- 断网且系统未安装 Node/Bun/Git 时可以启动、导入并使用基础房间。
- 房间代码不能直接调用 Node、任意文件路径和网络。
- Pi 可以通过受控工具修改一个房间并完成离线构建。
- 形成“继续、调整或停止 Electron 方案”的书面结论。

### 评审决策

- Electron 是否作为 MVP 外壳。
- 首批正式支持矩阵。
- 房间渲染进程隔离方案是否足够。
- 便携凭据采用何种默认策略。

## 4. 阶段 1：房间运行时原型

### 目标

将技术探针升级为可重复测试的房间平台核心，不追求完整 AI 对话体验。

### 交付物

- `.room 0.1` Schema、打包器和验证器。
- 房间注册表、标签和生命周期。
- Room SDK 1：storage、db、files、ui、基础 jobs。
- 权限记录、导入确认和权限变更流程。
- 程序/数据分离、迁移、备份和回滚。
- 受控自定义协议、CSP、IPC Schema。
- Windows/UOS 自动化兼容测试样例。

### 退出条件

- 五个手写参考房间通过合规性测试。
- 更新房间不会覆盖用户数据；迁移失败可以恢复。
- 非法路径、压缩炸弹、篡改哈希和不兼容版本被阻止。
- 基础能力完全离线运行。

## 5. 阶段 2：AI 创建 MVP

### 目标

让非程序员完成从需求到可分享房间的闭环。

### 交付物

- PiAdapter 与受控 Agent 工具集。
- AI 能力中心和 Provider 配置界面。
- API Key 保险库、连接测试和模型角色映射。
- 固定房间模板、组件目录和 SDK 检索。
- AI 对话、变更摘要、构建反馈、预览和检查点。
- Bun 房间构建器及禁止依赖扫描。
- 内置 Git 检查点和可视化 diff/恢复。
- `.room` 导出、完整性和本机签名。
- Windows 用户安装版、Windows 便携版、UOS 发行候选包。

### 退出条件

- 目标非开发用户无需命令行完成五个验收场景。
- 云 API 和内网 API 至少各一种稳定可用。
- 错误能够区分 Provider、构建、权限、数据迁移和运行时问题。
- 安装包首次启动不下载应用运行依赖。
- API Key 不出现在房间包、Git 和诊断包中。

## 6. 阶段 3：内网试点版

### 目标

在真实组织环境中验证管理、支持、安全和长期使用，而不仅是 Demo。

### 交付物

- 组织 Provider、证书、网络和权限策略包。
- 发布者签名与组织信任库。
- 离线 `.zupdate` 更新和回滚。
- SBOM、第三方许可证和安全响应流程。
- 脱敏诊断包与管理员诊断工具。
- 10 个以上真实模板及模板维护流程。
- 用户指引、管理员部署手册和支持流程。

### 退出条件

- 一个真实部门连续使用至少一个完整业务周期。
- 管理员可以仅凭文档完成离线安装、配置和更新。
- 高优先级安全问题有闭环处置。
- 收集到房间创建成功率、修改次数、失败类型和活跃使用数据。

## 7. 阶段 4：产品化与生态

只根据试点数据立项，不预先全部投入。候选能力包括：

- 组织房间库和审核工作流。
- 加密数据快照与跨设备迁移。
- WASM 扩展能力。
- 更完善的共享数据源和企业身份。
- 房间市场、模板生态和开发者 SDK。
- ARM64 与其他国产 CPU 支持。
- 多人协作和集中式策略管理。

## 8. 前四周推荐动作

### 第 1 周

- 访谈 5～8 名目标用户，收集三个真实工作流及示例数据。
- 锁定两台测试设备和准确系统版本。
- 确认房间规范 0.1 的最小字段和权限。
- 建立代码仓库、ADR、CI 和发行组件清单。

### 第 2 周

- 完成 Electron 多标签最小原型。
- 实现 `.room` 安全解包和自定义协议加载。
- 实现最小 SQLite/文件 Capability Broker。

### 第 3 周

- 嵌入 Pi，接入 OpenAI-compatible 内网测试服务。
- 调用内置 Bun 构建示例房间。
- 集成 MinGit 或目标平台 Git，并验证无 PATH 运行。

### 第 4 周

- 在 Windows/UOS 做端到端测试。
- 制作免管理员便携发行物。
- 评审安全、内存、包体和兼容结果。
- 更新 ADR，决定是否进入阶段 1。

若团队较小，可以延长周期，但不应跳过上述验证顺序。

## 9. 阶段评审模板

每个阶段结束时回答：

1. 本阶段的退出条件是否全部有证据？
2. 哪些假设被证伪，架构和 PRD如何更新？
3. 当前最大的三个风险是什么？
4. 下一阶段新增了哪些不可逆成本？
5. 是否有真实用户反馈，而不仅是研发自测？
6. 结论是继续、限范围继续、返工验证还是暂停？
