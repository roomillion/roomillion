# 千万间 Roomillion总体技术架构

## 1. 架构目标

本架构首先解决可分发、离线、权限隔离和跨平台问题，其次才是支持更多语言或包生态。基本策略是将平台相关能力放入工作台，将房间限制为可移植的 Web 资源、业务逻辑和声明。

## 2. 逻辑架构

## 3. 建议技术组合

| 层 | 建议 | 作用 | 说明 |
|---|---|---|---|
| 桌面外壳 | Electron | 窗口、标签、跨平台打包、Chromium 沙箱 | 阶段 0 必须在目标 UOS 验证 |
| 宿主进程 | Electron Main/Utility Process | 权限代理、生命周期和 Pi SDK | 使用 Electron 自带 Node，无需另装 Node |
| 房间 UI | TypeScript + 固定 Web UI 栈 | 业务界面与轻量业务逻辑 | 不允许自行选择任意框架和构建链 |
| 构建工具 | 内置 Bun | 脚手架、TS/TSX 构建、测试、依赖检查、打包 | 从固定资源路径调用，不读取系统 Bun |
| Agent | Pi SDK，经 `PiAdapter` 封装 | 多 Provider、会话和工具调用循环 | 不直接暴露 Pi 默认无限制工具 |
| 版本管理 | Windows MinGit / 目标 Linux Git | 检查点、diff、commit 和回滚 | 使用受控 Git 工具封装 |
| 数据 | SQLite | 房间数据和工作台元数据 | 每房间独立，不直接放网络共享盘并发写 |
| 高性能扩展 | Web Worker；未来可选 WASM Component | 重计算和可移植扩展 | MVP 不开放原生模块 |

## 4. 为什么不为房间提供传统后端

如果每个房间都可以启动 Bun/Node 服务，就会重新引入端口冲突、进程管理、任意文件权限、依赖下载和平台专属二进制。MVP 中，业务逻辑运行在房间渲染环境；需要特权的操作通过 Room SDK 请求工作台。

只有经过平台设计的后台任务才运行在宿主任务服务中。任务服务接收结构化参数，而不是接收房间提供的任意脚本路径。

## 5. 进程与信任边界

### 5.1 桌面主进程

可信，但保持最小职责：窗口、应用生命周期、自定义协议、权限路由和进程管理。主进程不加载房间 JavaScript。

### 5.2 房间渲染进程

按不可信代码处理：

- `nodeIntegration: false`
- `contextIsolation: true`
- `sandbox: true`
- 使用独立的 `room://<room-id>/` 来源
- 严格 CSP，默认禁止外部脚本、外部连接和弹窗
- 禁止任意导航和新窗口
- IPC 方法逐个暴露，不向页面暴露通用 `invoke(channel, payload)`

不同房间应有独立的逻辑来源和存储分区。阶段 0 需要测量每房间独立 WebContents 的内存成本，再决定非活动标签的冻结和恢复方式。

### 5.3 Agent 与构建进程

Pi 和 Bun 处理 AI 生成内容，不能与桌面主进程共享无边界权限。

- Agent 只看到房间虚拟工作区。
- Pi 默认 `read/write/edit/bash` 不直接启用，改用工作台注册的受控工具。
- Bun 仅执行工作台生成的固定构建入口和参数。
- 构建结果写入临时输出目录，经校验后才能进入房间包。
- 进程超时、输出大小、CPU/内存和并发数量应有限制。

仅靠工具白名单不等于强沙箱。阶段 0 需要评估 Windows 受限进程和 Linux 沙箱方案；在强隔离完成前，产品应限制为工作台生成或可信发布者签名的房间。

## 6. AI Gateway

AI Gateway 是房间和真实模型 Provider 之间的唯一通道。

```text
Room / Coding Agent
        │ logical role: coding | general | vision
        ▼
Permission + quota + audit
        ▼
Pi Provider Adapter
        ├─ OpenAI Responses / Chat Completions
        ├─ Anthropic Messages
        ├─ Google / Azure / Bedrock 等预置 Provider
        ├─ OpenAI-compatible 内网端点
        └─ 特殊接口扩展
```

### 6.1 Provider 配置

Provider 配置与 Pi 内部配置格式解耦，工作台维护自己的稳定模型：

```ts
interface ProviderProfile {
  id: string;
  name: string;
  protocol: string;
  baseUrl?: string;
  credentialRef: string;
  proxyPolicy: "system" | "direct" | "custom";
  certificateProfile?: string;
  models: ModelProfile[];
}
```

`PiAdapter` 在运行时将其转换为 Pi Provider。这样 Pi 升级、字段变化或未来替换实现时，不需要迁移所有房间和用户配置。

### 6.2 密钥策略

- 安装版优先使用操作系统凭据存储，并在工作台数据库中只保存引用。
- 便携版提供“每次输入”或“主密码加密保险库”两种模式。
- 不以设备路径、机器标识等可预测信息作为唯一加密密钥。
- 密钥不进入房间进程、Git、普通日志、崩溃转储和房间包。
- 管理员 Provider 模板与用户个人密钥分别管理。

## 7. Capability Broker 与 Room SDK

Room SDK 是稳定的业务 API，Capability Broker 是宿主实现。建议首批能力：

| 能力域 | 示例 | 默认权限 |
|---|---|---|
| `room.storage` | 少量键值设置 | 房间私有，可直接使用 |
| `room.db` | 参数化查询、事务和迁移 | 房间私有，可直接使用 |
| `room.files` | 选择、读取和导出文件 | 需要用户手势或授权句柄 |
| `room.ai` | 按逻辑模型角色调用 AI | 需要房间 AI 权限 |
| `room.jobs` | 运行官方定义的后台任务 | 按任务类型授权 |
| `room.ui` | 通知、对话框、主题 | 基础能力 |
| `room.clipboard` | 读写剪贴板 | 读取需明确授权 |
| `room.network` | 通过宿主代理访问 Manifest 精确声明的 HTTP/HTTPS 源 | 默认关闭；需全局开关、房间声明和逐源授权 |

所有 IPC 参数和返回值使用可校验的结构化 Schema。数据库查询必须参数化；文件能力返回受控句柄，不直接返回任意宿主绝对路径。

`room.ai` 与 `room.network` 是相互独立的能力：AI Gateway 可继续连接用户配置的云端或内网模型 API；主工作台的房间联网总开关只控制普通房间业务请求。房间渲染进程仍禁止直接 `fetch`、XHR、WebSocket 和导航，所有允许的业务请求由 Capability Broker 校验目标源、权限、跳转、大小和超时后代发。

## 8. 共享资源模型

### 8.1 可以共享

- Room SDK 运行时。
- 标准 UI 组件、图标、图表和文档处理能力。
- SQLite 引擎、AI Provider 实现和 Git/Bun 工具。
- 按哈希存放的只读资源对象。
- 管理员授权的共享数据源。

### 8.2 必须隔离

- 每个房间的 SQLite 数据库。
- 房间私有文件和缓存。
- 房间权限记录。
- AI 会话及敏感上下文。
- 构建临时目录。

### 8.3 不采用共享 `node_modules`

共享可写 `node_modules` 会产生版本漂移、依赖污染、原生模块冲突和不可重复构建。官方组件由工作台版本化提供；特殊依赖必须在构建期锁定、审计并随房间或离线资源层携带。

## 9. 数据布局建议

以下为逻辑布局，具体路径由不同平台映射：

```text
WorkbenchData/
  workbench.db
  providers/
  certificates/
  rooms/
    <room-id>/
      app/             # 已验证的只读房间程序
      data/
        room.db
        files/
        cache/
      checkpoints/
      permissions.json
  objects/             # 内容寻址的共享只读对象
  logs/
  updates/
```

程序更新只替换 `app/`，数据迁移只操作 `data/`，并在迁移前创建检查点。

## 10. 房间导入流程

```text
选择/拖入文件
  → 限制文件大小和解压比例
  → 在隔离临时目录解包
  → 防止绝对路径和 ../ 路径穿越
  → 校验 manifest、哈希和签名
  → 检查 SDK/工作台兼容性
  → 展示新增权限
  → 用户确认
  → 原子安装或更新
  → 首次启动与健康检查
```

## 11. 可观测性

- 工作台日志、Agent 日志、构建日志和房间控制台分开。
- 每次 AI 生成、构建、权限变化、导入和迁移产生关联 ID。
- 用户可导出脱敏诊断包。
- 日志默认不记录完整提示中的敏感文件内容，不记录凭据和授权头。
- 离线环境的日志同样可用于定位运行时版本和兼容问题。

## 12. 阶段 0 必须验证的架构假设

1. Electron 在指定 UOS 版本上的启动、渲染、输入法、文件选择和沙箱行为。
2. 同一个 `.room` 在 Windows/UOS 的 UI 与 SQLite 行为。
3. Electron 自带 Node 中嵌入 Pi SDK的可行性。
4. 内置 Bun 构建固定房间模板时能否做到零联网。
5. Windows MinGit 和 Linux 内置 Git 在隔离配置下的行为。
6. 多房间 WebContents 的内存占用和冻结恢复。
7. API Key 在安装版和便携版的安全存储体验。
8. 房间导入和数据库迁移的失败回滚。
