# 多模型中心与房间 AI 选择接口

## 1. 本轮目标

千万间 Roomillion把“连接提供商”和“启用模型”拆成两个明确层级：同一个提供商只需配置一次凭据，就能一次启用多个模型。每个房间开发 Agent 会话都可以选择自己的编程模型；获 AI 权限的房间也可以读取主工作台提供的脱敏模型目录，保存一个或多个角色的模型选择并调用，不需要、也不能再次读取或保存用户的 API Key。

## 2. 用户流程

1. 打开“AI 能力中心”。默认只显示“已连接提供商”和每个提供商下面的“已启用模型”，添加表单不会混在列表中。
2. 点击“添加提供商”，选择 Pi Provider，填写一次 API Key。
3. 在可搜索模型目录中勾选一个或多个模型。每项显示模型 ID、上下文长度、推理和图片能力；已启用项会明确标注并锁定，不能重复导入。
4. 点击“启用所选模型”即可批量创建配置。自定义 OpenAI-compatible 服务使用“每行一个模型 ID”的文本规则，一次最多启用 50 个。
5. 以后点击该提供商的“管理 / 添加模型”，工作台会复用现有安全凭据；若不希望共用，可点击“改用新 Key”。
6. 在“设置 → AI 能力”或“AI 能力中心”顶部直接查看和切换“房间默认 AI 模型”。它用于未单独选择模型的房间，也是新建 AI 对话的初始模型；批量新增同连接模型不会意外改变原默认项。
7. 进入“AI 创建房间”后，在对话顶部“编程模型”选择器中为当前会话选模型。选择会随会话保存，后续消息和恢复后的对话都继续使用它；Agent 运行中不能切换。
8. 单模型房间调用 `window.room.ai.listModels()` 展示可用项，再调用 `selectModel(id)` 保存本房间选择。
9. 房间调用 `generate(prompt)` 时，主进程使用该选择对应的凭据发起请求；多角色房间则为每个角色保存独立的配置 ID，并调用 `generate(prompt, { profileId })`。

## 3. 安全边界

- API Key 只保存在主进程内存或按配置拆分的系统加密文件中。
- 普通配置文件、房间文件、Git 历史和 Room SDK 返回值都不包含 Key。
- 房间拿不到自定义 Provider 的 `baseUrl`，避免将内网拓扑暴露给不受信任房间。
- 所有房间模型接口都先按 WebContents 识别房间，再检查该房间是否获得 AI 权限。
- 房间传入的配置 ID 必须存在于主工作台注册表中。
- “管理 / 添加模型”只把来源配置 ID 和本次勾选的模型 ID 交给主进程；AiService 会校验来源配置存在、Provider 与服务地址完全一致且凭据可用。API Key 不会返回渲染进程。
- 如果用户选择系统安全存储，新增模型获得独立的加密凭据副本；删除一个模型不会破坏同一 Provider 的其他模型。

## 4. 兼容与迁移

旧版 `provider.json` 和 `provider-secret.bin` 在启动时自动迁移为 `formatVersion: 0.2` 的多配置注册表与 `provider-secrets/<配置ID>.bin`。旧的 `window.room.ai.generate(prompt)` 无需修改；没有房间级选择时自动使用主工作台默认模型。

## 5. 房间内推荐交互

房间若需要让用户切换模型，应使用 `label` 作为主标题，以 `providerName · model` 作为说明，并标注 `supportsImages`、`contextWindow`、`ready`、`isDefault`。收到 `onModelsChanged` 通知后重新读取目录。不要在房间中提供 API Key 输入框。

单模型房间使用 `selectModel(profileId)` 即可；该方法会更改房间自己的默认选择，但不改变主工作台默认模型。多角色房间不要在角色轮换时反复调用 `selectModel`，而应把各角色的配置 ID 存入房间设置，并按次路由：

```js
const models = await window.room.ai.listModels();
const positiveProfileId = models.find((item) => item.ready)?.id;
const result = await window.room.ai.generate(positivePrompt, {
  profileId: positiveProfileId
});
```

需要图片理解的房间必须申请 `ai.vision`，筛选 `supportsImages: true` 的配置，并把真实图片二进制交给 Gateway：

```js
const result = await window.room.ai.generate(prompt, {
  profileId,
  images: [{ mimeType: "image/png", data: pngBytes }],
  maxTokens: 800,
  temperature: 0,
  structuredOutput: true
});
```

Gateway 会校验图片内容、体积、数量、房间权限和模型能力。房间不应把图片转换成外部 URL，也不应直接访问模型端点。

这里传递的是工作台生成的配置 ID，不是 API Key。模型调用仍由主进程 `AiService` 执行，房间无法读取凭据和自定义服务地址。

## 7. alpha.18 易用性改造

本轮借鉴 OpenCode 将提供商连接与模型选择分开的做法，但针对非程序员改成可视化批量流程：

- 已连接区按 Provider 与服务地址分组，不再把每个模型伪装成一个独立“提供商”。
- 添加区默认收起；只有用户主动添加或管理时展开三步流程。
- 内置目录支持搜索、多选、全选未启用和清空；已启用模型保持可见但禁用。
- 同一连接的模型复用主进程凭据；系统安全存储仍为每个模型保留独立加密副本，删除单个模型不影响其他模型。
- AI 创建房间的模型选择从“全局默认”升级为“每个会话独立选择”，运行时把 `profileId` 直接传给 Pi Agent runtime。
- 房间侧仍使用同一个 `window.room.ai` 接口，可为单角色保存房间默认模型，也可为不同角色分别传入 `profileId`。

Electron 冒烟会真实执行 MiMo 首次连接和追加模型流程，检查添加区初始收起、模型目录可多选、已启用项锁定、Key 不返回页面、两个模型凭据均可用、追加模型不改变默认项，并继续验证真实房间的 `listModels`、`getSelection` 和 `selectModel`。

## 8. 目录外模型：自动获取与手动添加

内置 Pi 目录离线生成，服务商上新模型后工作台可能暂时没有对应条目。为此提供两条补充路径，均只作用于 OpenAI 兼容协议（`openai-completions`）的目录提供商，例如 MiMo Token Plan、Kimi、DeepSeek、通义千问 Token Plan 等；目录条目会标注 `supportsModelFetch`，不满足条件（如 openai-responses/anthropic/google、OAuth 或按模型独立端点）的提供商显示“暂不支持自动获取”，仍可手动添加，但按模型独立端点的提供商手动添加会被拒绝。

- **自动获取**：提供商编辑器内点击“从服务商获取最新模型”，主进程用 `GET {baseUrl}/models` 拉取模型 ID。密钥优先使用编辑器中刚输入的明文，其次复用该提供商任一已启用配置的会话密钥；密钥只用于本次请求，不落盘、不写日志、不返回渲染进程。返回的 ID 经清洗（去重、长度与字符集校验）后合并进勾选列表，标注“服务商返回”。
- **手动添加**：在“手动添加模型 ID”输入框按行填写；与目录内模型勾选可同时启用。
- **能力声明**：目录外模型缺少官方目录元数据，添加时由用户声明能力——上下文长度（默认 128000）、是否支持图片输入、是否支持音频输入。图片、音频开关分别决定图片、音频请求是否放行；音频经 `room.ai.generate(prompt, { audio })` 以 OpenAI 兼容的 `input_audio` 块实际传输（需房间获 `ai.audio` 权限，wav/mp3/ogg/flac/m4a/webm 魔数校验，单文件 ≤64 MiB，仅 openai-completions 协议；OpenAI 官方接口仅接受 wav/mp3，其余格式取决于服务商网关），模型目录提供 `supportsAudio` 供房间筛选。最大输出固定按 8192 预留。
- **存储与运行**：目录外模型在 profile 中记录 `modelSource: "custom"` 与 `modelCapabilities`（不含任何密钥），注册表格式仍为 0.2，旧数据无需迁移；运行时按 OpenAI 兼容协议构造模型，未声明 `modelSource` 的目录外模型仍被“所选模型不属于当前 Provider”闸口拒绝。
- **房间侧不变**：目录外模型经 `listRoomModels` 正常列出（能力来自用户声明），房间仍拿不到 baseUrl、协议与密钥。
